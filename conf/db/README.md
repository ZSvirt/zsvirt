# SQL 目录与版本映射

**不管闭源发布了多少个版本，若积攒着开源没发布，就不应该冻结upgrade目录下的开源产品版本，而是继续使用开发版本。**

这里的产品版本指 `1.0.1 -> 1.0.2`，开发版本指 `1.0.1.5 -> 1.0.1.6`。
SQL 编号属于当前待发布的开源版本；只有开源实际发布后，下一轮开发才切换产品版本。

## 目录与映射

| 目录 | 用途 |
| --- | --- |
| [upgrade/](upgrade/) | 主库源 SQL，统一在这里编写，使用开源编号 |
| [ee/](ee/) | 闭源（EE）编号到源 SQL 的相对符号链接 |
| [ee-history/](ee-history/) | 旧商业版本的历史 SQL，保持不变 |
| [zstack_rest/upgrade/](zstack_rest/upgrade/) | REST 库的独立迁移，与主库分开 |

例如，开发闭源 `5.2.1`、待发开源 `1.0.1` 时，可以新增：

```text
ee/V5.2.1__schema.sql -> ../upgrade/V1.0.1.5__schema.sql
```

映射两侧应代表累计数据库变更等价的检查点。同一份源 SQL 只映射一个 EE 编号。

## 开发规则

1. **闭源开工时新增 SQL 和映射。**在当前待发开源版本下递增编号；没有数据库变更，也创建空 SQL 和独立映射。
2. **开发中只修改本次未发布的 SQL。**只写新增变更，不复制历史 SQL。闭源一旦开工，开源必须等本轮闭源发布后才能发布，不需要提前判断是否同步发布。
3. **闭源发布后冻结本次文件。**SQL 的文件名、内容及映射目标都不能再改；开源未发布，后续闭源仍在当前产品版本下追加开发版本。
4. **开源实际发布后才切换产品版本。**开源复用最后一次闭源已交付的 SQL 迁移链，不另建 SQL 或改映射。下一轮新建 `V1.0.2__schema.sql`，后续闭源迭代再用 `V1.0.2.1__schema.sql`。

“冻结本次文件”不等于“冻结产品版本”：已发布文件始终不改，当前产品版本可以继续追加开发版本。

## 开发流程

```text
                         新闭源版本开工
                                |
                                v
                当前待发版本下新建 SQL 和 EE 映射
                                |
                                v
                只修改本次 SQL；无变更保留空文件
                                |
                                v
                  闭源发布，冻结本次 SQL 和映射
                                |
                                v
                       开源是否实际发布？
                +---------------+---------------+
               否                              是
                v                               v
      下一闭源继续开发版本           复用当前检查点发布开源
       1.0.1.5 -> 1.0.1.6               下一轮切到 1.0.2
```
